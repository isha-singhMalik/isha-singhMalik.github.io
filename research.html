Security Research Log

Passive OSINT reconnaissance, honest outcomes, and what each result taught me

I find exposed and misconfigured infrastructure using passive techniques only: certificate transparency logs, search-engine dorking, DNS and CNAME analysis, and public cloud-storage checks. I never exploit, claim, or access anything beyond what is publicly visible.

This page lists every report I have submitted, including the ones that were rejected or are still unanswered. Triage decisions are part of the skill, so I show them as they happened.

Disclosure note: Company and program names are withheld because most bug bounty programs restrict public disclosure of reports. Severities shown are my own assessment at the time of reporting, not the vendor's rating. Details are available to interviewers on request.

Case studies

ValidatedHackerOne

Public cloud-storage listing across four buckets

What I found

A search-engine dork for the company's storage domain surfaced one bucket with directory listing enabled. Checking the naming pattern showed three more with the same misconfiguration, so the problem was systemic rather than a single mistake.

Outcome and lesson

Triage replied that another researcher had reported it first, and confirmed the finding was real. My method was sound. I lost on timing because I spent hours mapping every bucket before reporting. I now report the first confirmed instance immediately and mention the pattern.

Closed N/ADirect

Authentication subdomain with an unreachable origin

What I found

An accounts subdomain returned 404. Its CNAME chain led through an identity-platform alias to a CDN whose origin could not be contacted. I verified each hop and reported it as possible abandoned authentication infrastructure.

Outcome and lesson

The vendor replied that a non-functional subdomain is a functional bug, not a security bug. They were right that I had not shown a claimable resource or any data exposure. Now I only report a dangling DNS record when I can show the third-party resource is unclaimed, or the impact is concrete.

ClosedDirect

Version disclosure on a hosting provider's server-status page

What I found

A public server-status page exposed the Apache and OpenSSL versions. I matched them to published CVEs and rated the finding critical.

Outcome and lesson

The operator explained that the versions were current, that each customer's code runs under its own user ID, and that they track the upstream security lists. Listing CVEs against a banner is not the same as showing exploitability. I now check whether the version is actually outdated and what mitigations exist before assigning any severity.

What I chose not to report

These were investigated and set aside. Knowing when not to submit protects the reviewer's time and my credibility.

  • Subdomains on staging, internal, or deprecated systems, where the name and behaviour pointed to intentional restriction.
  • Subdomains whose CDN or provider could not be claimed, so there was no takeover path.
  • Public company details, sitemaps, navigation APIs, and robots.txt content that are meant to be public.
  • An academic server with a restricted status endpoint, where the risk-to-reward balance did not justify contact.
  • Targets with no clear security contact or an unclear disclosure process.

What the results taught me

  • Read scope before hunting. A finding can be real and still earn nothing when it sits outside a program's bounty tiers.
  • Functional and security bugs are different. Show an attacker's gain, not only that something is broken.
  • A CVE match is not exploitability. Check version currency and mitigations first.
  • Speed matters on obvious misconfigurations. Report the first confirmed instance, then extend.
  • Ask when scope is unclear. I submit one report, state the uncertainty, and wait before sending more.

Method

Discover

Certificate transparency logs, dorking, DNS and CNAME resolution, cloud-storage naming patterns.

Verify

Confirm each hop of the chain and test only what is publicly reachable, with no exploitation.

Judge

Check scope, mitigations, and attacker impact before deciding to report.

Report

Reproducible steps, evidence, honest severity, and a concrete fix.
